# 就地助手面板（V2）

最后更新：2026-09-19，版本 **0.8.1**。本文与实现保持一致。

目标：让用户在**不离开当前应用**的情况下获得沟通分析 —— 即产品总纲里"悬浮助手是核心入口"的落地。

## 为什么是这个形态

最初计划是"点悬浮球 → 框选截屏 → OCR → 分析"，让助手读取屏幕。两条自动读取路径都验证过：

- **无障碍读界面**：实测微信不向无障碍框架暴露任何内容（见 [无障碍 PoC](A11Y_READABILITY_POC.md)），**已否决**
- **截屏 OCR**：用户关闭 HyperOS「屏幕共享保护」后**可用**（见 [面板内截屏分析](PANEL_CAPTURE.md)）

因此助手同时支持两条取内容的路，且都以**用户主动触发**为前提：

| 路径 | 是否需要关闭屏幕保护 | 说明 |
| --- | --- | --- |
| **手动粘贴 / 剪贴板** | 否 | 任何设备都可用 |
| **截屏分析（框选）** | 是 | 依赖 MediaProjection，受屏幕共享保护影响 |

两条都符合总纲的 Just-in-Time Context（用户主动调用、只获取必要内容、不持续监听）。

## 实现

| 文件 | 作用 |
| --- | --- |
| `ui/panel/AssistantPanel.kt` | 面板本体（Compose）：输入、分析、状态与建议、候选回复、复制 |
| `ui/panel/AssistantPanelState` | 面板状态，**在视图重建时保留**（见下） |
| `system/AssistantPanelWindow.kt` | 把面板挂成 `TYPE_APPLICATION_OVERLAY` 窗口；自备 lifecycle / ViewModelStore / SavedStateRegistry |
| `system/FloatingAssistantService.kt` | 悬浮球；点击**打开面板**（原先只是把应用拉到前台，那是装饰） |
| `MainActivity` | `--ez show_assistant true` 可直接打开面板 |
| `ui/home/HomeScreen.kt` | 「打开助手面板」按钮，不依赖悬浮窗也能用 |

**关键实现点**：

- 面板窗口用 `FLAG_NOT_TOUCH_MODAL | FLAG_WATCH_OUTSIDE_TOUCH`，高度 `WRAP_CONTENT`、`Gravity.BOTTOM`，只占底部一块，**下面的应用仍然可见**，这正是"就地"的含义。
- 上限取**屏幕高度的 68%**（不是写死的 dp），换设备自动适配。
- `softInputMode = ADJUST_RESIZE`：键盘弹出时面板随可用空间伸缩，而不是被整体推上去。
- **每次挂载都新建 `LayoutParams`，挂起/关闭用 `removeViewImmediate`**。
- 截屏返回时**重建视图**而非重挂旧视图，用户文字与结果存在 `AssistantPanelState` 里，不会丢。
- 复用与应用相同的 `ConversationRepository` + `MockLlmService`，面板结果与完整界面一致。

> **关于"重建视图"**：把 `removeViewImmediate` 摘下的同一个 View 再 `addView` 回去，窗口能显示、`isVisible=true`，但**输入链路没有重建** —— 整个面板"看得见、按不动"。这是 0.8.1 修掉的缺陷，详见 [面板内截屏分析](PANEL_CAPTURE.md)。

## 布局适配（实测三种屏幕）

| 配置 | 结果 |
| --- | --- |
| 1080x2400 @420dpi | ✅ |
| 720x1280 @320dpi（小屏低密度） | ✅ 元素全部在屏内，面板缩到约 60% 屏高 |
| 1280x720 @320dpi（横屏） | ✅ 超出屏幕的元素数 0 |

布局使用 dp（密度无关）与 `weight(1f)`（按剩余空间等分），因此换设备自动适配；唯一按屏幕比例计算的位置是悬浮球的初始纵坐标。

## 关于截屏路线的复核（用户关闭屏幕共享保护之后）

用户关闭了 HyperOS 的屏幕共享保护（`screen_share_protection_on = 0`），因此重新复核了"截屏能否读到微信"：

| 证据 | 结果 |
| --- | --- |
| `settings get secure screen_share_protection_on` | ✅ 已为 `0` |
| `screencap`（系统级截图） | ✅ 463.7 KB，画面正常 |
| `screenrecord`（与 FlowAI 用同一套 MediaProjection） | ⚠️ 3 秒仅 67.6 KB，**且关闭保护前也是同一数量级** |

**结论：未能确认。** 两条线索互相矛盾：

- `screencap` 正常，说明屏幕内容本身可被捕获
- `screenrecord` 体积异常且关保护前后一致，暗示 **MediaProjection 在这台设备上可能整体受限**（HyperOS 或把录屏能力保留给系统自带录屏）

因此**不能仅凭"关闭了保护"就断定 FlowAI 的截屏能拿到画面**。要定论需要看实际帧内容（帧亮度统计），而这需要一个可用的 APK 加上人工授权。

**结论（已定论）**：关闭保护后**截屏可用**。帧亮度统计显示非黑屏（`frame 880x500 avgLuma=227 nonBlackSamples=448/448`），真机也成功识别出文字。现已在面板内作为「截屏分析」入口提供，见 [面板内截屏分析](PANEL_CAPTURE.md)。

| 交互 | 行为 | 验证 |
| --- | --- | --- |
| 点「收起」 | 收起 | 模拟器 ✅ |
| 点面板**外部** | 收起 | **真机人工确认 ✅** |
| 点「在完整界面中打开」 | 先收起面板，再打开完整界面 | 模拟器 ✅（覆盖窗口 2 → 1） |

注：原先声明了 `FLAG_WATCH_OUTSIDE_TOUCH` 却**从未处理 `ACTION_OUTSIDE`** —— 声明该标志本身不会做任何事，因此点外部不收起。已用 `OutsideTouchFrameLayout` 修好。

## 已知限制

- **重装 APK 会清除"显示在其他应用上层"权限**（HyperOS 行为），需重新授权；首页已加提示。
- **adb 无法驱动悬浮球**：注入的触摸到不了覆盖窗口（系统安全限制），所以"点球开面板"这一步只能人工验证。
- **面板按键在截屏后会失效**：这是 0.8.1 修掉的真实缺陷（重挂旧视图导致输入链路未重建），现已改为重建视图。
- **输入方式**：目前是手动输入、粘贴剪贴板、或截屏分析三者。**理想形态是配合划词入口** —— 微信里选中文字 → 用 FlowAI 分析 → 面板带着这段文字直接弹出，省掉粘贴动作。尚未接通。
- **说话人推断有局限**：基于左右分栏，居中气泡、群聊多人、整行满宽的消息不会被归属。
- 面板是只读展示 + 复制；不写入日历/待办，不自动发送。
- 仍是 Mock 引擎：内置案例有固定演示结果，其他文本走通用模板。
